# Decision Log — Discount Code at Checkout PRD

## 2026-05-19 — Initial creation (fast-path, agent-driven)

| # | Decision | Rationale | Alternatives considered |
|---|----------|-----------|------------------------|
| 1 | Discount applied at `POST /orders` only | Checkout is the only creation point; no amendment endpoint exists | Apply via separate `PATCH /orders/{id}/discount` — rejected, adds complexity for no gain |
| 2 | Allowed percentages: 5, 10, 20 only | Explicitly stated in the request | Open-ended float percentage — out of scope for v1 |
| 3 | No expiry or single-use tracking in v1 | Simplest thing that works; scope is narrow | `expires_at` + `used` flag — deferred to v2 |
| 4 | `discounted_total` stored as integer cents alongside `total` | Consistent with existing `_to_cents()` pattern in the codebase | Store as float or derive at read time — both rejected: float precision risk, derived field adds query complexity |
| 5 | No admin API in v1; codes seeded in DB directly | Scope explicitly excludes code management; out-of-band seeding is sufficient | `POST /discount-codes` admin endpoint — deferred to v2 |
| 6 | Rounding via Python `round()` | [ASSUMPTION] — flagged as open question #2 for PM confirmation | `math.floor` or `math.ceil` — held open |
| 7 | Response fields null (not omitted) when no discount applied | Consistent schema for all callers; easier to consume | Omit fields — held open as open question #3 |
